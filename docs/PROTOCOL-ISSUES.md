# 协议层问题台账

> 客户端开发期间发现的问题记录在此，**不在客户端变更里顺手改协议层**，
> 攒一批后单独提交（修复 + 本台账销账）。登记时写清楚：现象、根因、
> 影响面、建议修法（若已明确）。条目编号 P<n> 递增，销账保留条目并标注。

## P1 mdns_test 依赖单调时钟推进，Windows 上必挂

- **发现**：2026-10-19，Windows 客户端立项当日跑 `cd protocol && go test .`
- **现象**：`TestMdnsBrowserPrune` 5/5 稳定失败：「过期设备应被淘汰 1 台，实际 0」
- **根因**：测试靠「时间自然流过」让 `time.Since(LastSeen) > 0` 成立，但 Windows
  Go 单调时钟粒度约 0.5ms，测试全程仅数十微秒，`Since` 返回精确 0。Linux
  纳秒级时钟上必过，属平台可移植性缺陷（测试写法，非库逻辑——`Prune` 的
  `> maxAge` 语义本身正确）。
- **建议修法**：测试内显式回拨 `LastSeen`（同包可直接改 map），不赌时钟；
  已在本地工作区按此修（+11 行，test-only），待独立提交
  `fix(protocol): mdns prune 测试适配 Windows 时钟粒度`。

## P2 mDNS TXT `encryption` 枚举缺 DirectLink TCP/TLS 取值

- **发现**：2026-10-19，windows-connection 里程碑设计时
- **现象**：§3.2.1 TXT 表中 `encryption` 只枚举 `"dtls13" / "none"`，而 §7.2
  DirectLink TCP 模式的传输加密是 **TLS 1.3**——现枚举没有能如实声明它的值。
  客户端只能填扩展值 `"tls13"`（字符串字段，消费方不应硬失败）。
- **建议修法**：§3.2.1 表增补 `tls13`（DirectLink TCP/TLS），或把该字段语义
  改为「传输加密能力自由串 + 已知值枚举」。记入下次协议修订。

## P4 §9.1 心跳「收到即回」在双向角色下产生回显放大风暴

- **发现**：2026-10-19，windows-input 里程碑的双进程环回冒烟（间歇性
  「在线但零延迟样本」）
- **现象**：握手完成后心跳帧指数级自增——36 秒实测 **29.5 万帧**（trace 实锤），
  CPU 被回显循环打满，延迟采样/业务帧全部被饿死；是否在观测窗口内恶化
  取决于时序，故表现为间歇性。
- **根因**：§9.1 规定「接收方收到后立即回复 HEARTBEAT」，同时双方又各自
  周期发送（`发送方：每 2 秒发送`）。Role=0x03（双向）时两侧都是发送方 +
  回复方：每收 1 帧回 1 帧，回出去的又被对端回——1:1 无限放大。
- **建议修法**：规范明确二者取一——(a) 心跳由**单侧角色**周期发送、对端
  回复（Host↔Target 语义下成立）；或 (b) 双向各自周期发送、收帧仅作喂狗
  不回帧。客户端已按 (b) 实现。
- **销账进展**：2026-10-20，macOS 客户端 `PeerSession` 亦已按 (b) 修复
  （原「收到即回」已移除），并补回归测试 `heartbeatsDoNotEcho`；
  Windows 端此前已按 (b) 实现。规范侧 §9.1 措辞仍待修订（本条保留）。

## P5 cgo 桥没有暴露 mDNS 发现，客户端发现不出一台对端设备

- **发现**：2026-10-21，deepin 客户端把「设备与连接」「添加设备」两屏的假数据
  换成真实数据时
- **现象**：`protocol` 包里有完整的 `mdns.go` / `discovery.go`（编码 + 浏览器
  状态机 + `Prune`），但 `cgo/bridge.go` 只导出了帧编解码、载荷、键位表、
  BLE/WiFi Direct 编码、RSSI 分类、延迟监视器这几组——**没有任何发现相关
  的导出**。于是客户端没法列出局域网里的对端：设备清单里只有本机，
  「添加设备 → 网络中的设备」永远是空的。
- **影响面**：设备发现、配对码、一次性配对码生成这三件事都做不了；
  键鼠共享、剪贴板同步、文件传输在接上对端之前无法开始。
- **建议修法**：在 `cgo` 里补一层薄导出——`fg_mdns_browser_new` /
  `fg_mdns_browser_poll`（返回发现到的设备条目）/ `fg_mdns_browser_free`，
  条目结构用扁平 C struct（name/address/platform/port/encryption）传，
  不要把 Go 的 map 指针漏到 C 侧。配对码另出一组
  `fg_pairing_code_generate`（现在界面上那四个点是**占位**，界面已如实标注
  「配对码由传输层密钥协商生成，传输层尚未实现，当前为占位」）。
- **客户端现状**：设备清单里如实列出**本机**（真实主机名 / 发行版 / IP），
  对端数为 0 并显示「仅本机」；配对屏显示「未发现设备 · 设备发现尚未接通」。

## P6 传输层（L3）未落地，客户端拿不到「对端延迟」

- **发现**：2026-10-21，同上
- **现象**：`protocol` 包没有任何 `net.Listen` / `net.Dial`，没有会话建立与
  收发循环；心跳的 ping/pong 也无从发往对端。
- **影响面**：「网络延迟」这一屏没有可测对象。
- **建议修法**：先落地 DirectLink（局域网 TCP/TLS）这一条最短路径：监听 →
  握手 → 心跳 → 业务帧，mDNS 只负责宣告与发现。
- **客户端现状（重要口径）**：延迟读数**不再编**。早先这一栏是每 2 秒
  `QRandomGenerator` 摇一个 2.4/3.1/11.6ms，数字在跳却从没量过；现在改成
  真实测量——用系统 `ping` 测**本机到默认网关**的 ICMP 往返，统计照旧交给
  Go 的 `LatencyMonitor`（口径与协议一致：读数是半 RTT，即单程时延）。
  界面上明确标注「实测网关 192.168.31.1 · ICMP RTT÷2」，不冒充「到对端的
  延迟」。传输层落地后，把测量目标换成对端即可，其余不动。

## P7 LAN 通告无新鲜度，可重放劫持地址 / 维持幽灵设备

- **发现**：2026-10-21，IntelligentLink 协议层加固时
- **现象**：§3.1.1 的通告只有 Version/Platform/Caps/Port/Name/PubKey/签名，
  **没有时间戳、序号或 nonce**，签名也只覆盖通告自身字段、不覆盖来源地址；
  `LanIDListener.Feed` 又直接用源 IP 覆盖已记录的 `Addr`。任何能抓到一帧
  通告的人都可以原样重放：把某台已下线设备的 `Addr` 改成自己的 IP（随后
  冒充它接受直连），或让一台永远不再上线的设备长期留在设备表里。
- **影响面**：设备发现投毒、连接被引向错误地址；周期通告让旧包看起来永远
  新鲜（`lastSeen` 只能证明「最近有人重放」）。
- **建议修法**：通告加 `Timestamp`（Unix 秒）+ `Nonce` 并纳入签名；监听侧
  拒绝过旧（如 >10s）与重复 nonce 的包。地址归属要么不写进通告、只用源 IP
  （并接受 NAT 语义），要么由签名显式绑定。重放窗口仍需靠 nonce 缓存封死。

## P8 发现组播与 IntelligentLink 数据共用 24801/UDP，demux 未定义

- **发现**：2026-10-21，同上
- **现象**：§3.1.1 规定通告发往 `239.255.42.99:24801`，并注明「与直连
  一致」；附录 A 又把 `24801/UDP` 定义为「IntelligentLink HID 数据传输 +
  DTLS」。也就是说同一个 UDP 端口同时承载**明文签名通告**与**DTLS 记录**，
  但规范没有给出两者如何区分（DTLS record 首字节 20..23，通告首字节 0x01，
  实际可以按首字节分流，但这是实现的隐式约定，第三方只能猜）。
- **影响面**：跨实现互通风险；未来接 DTLS 时若先按 DTLS 解析，会把发现包
  当成畸形记录丢弃并可能触发告警。
- **建议修法**：附录 A 明确「24801/UDP = 发现明文 + DTLS，首字节 <0x14
  为通告」；或给发现单独分配端口（如 24802/UDP），彻底消除复用。

## P9 身份指纹与 TLS 证书指纹是两套信任，互不绑定

- **发现**：2026-10-21，核对 Windows DirectLink 与 lanid 身份实现时
- **现象**：§3.1.2 的身份指纹是 `hex(SHA-256(IdentityPubKey)[0:16])`，
  信任链记录的也是它；而 Windows `link/identity.go` 的 TLS pin 是
  `hex(SHA-256(cert DER)[0:16])`。通告与 IDENTIFY 都不携带 TLS 证书或
  「身份私钥对证书/握手 transcript 的签名」，所以「我信任这个身份」无法
  推出「我连的就是这个身份的 TLS 端点」。中间人可以拿自己的证书与受害者
  的身份通告拼在一起，首次连接时人工核对的是身份指纹，实际 TLS 却指向别人。
- **影响面**：私有链信任（P-256 身份）与传输认证（TLS 证书）各说各话，
  配对确认的语义被架空。
- **建议修法**：让二者同源——TLS 证书直接用身份密钥签发（证书公钥 =
  IdentityPubKey，或用身份私钥签 CSR），pin 改为校验证书公钥指纹与
  IdentityPubKey 一致；握手 transcript 再由身份私钥签一次，把
  「发现到的身份 / 握手对端 / 证书」绑成一条可验证链。

## P10 TrustChain 无 Export/Import，重启即失忆

- **发现**：2026-10-21，同上
- **现象**：`TrustChain` 只有内存态，`cgo` 仅导出 `fg_trust_chain_count`，
  没有序列化/反序列化接口；客户端重启后信任记录全丢，「已拒绝」的设备
  可以重新弹确认，「已信任」的设备又要人工核对一次。
- **影响面**：§3.1.3 承诺的「后续自动信任」实际不成立；用户每次启动都要
  重新确认，最终会养成无脑点信任的习惯。
- **建议修法**：提供 `TrustChain.Export()/Import()`（带格式版本号；导入时
  逐条验签并重算 PrevHash），cgo 以字节缓冲导出/导入；客户端落到用户配置
  目录并原子替换。导入失败要保留旧链而不是清空。

## P11 SCROLL 规范写「像素」，三端实现实际用「格/行」

- **发现**：2026-10-21，修 Windows 滚轮 120 倍放大时
- **现象**：§5.3 把 `SCROLL` 的 `deltaY/deltaX` 定义为像素；但 macOS 捕获
  直接送 `CGEvent` 的 line delta（一格 = 1），Windows 捕获送的是
  `WHEEL_DELTA` 的倍数（一格 = 120），注入侧再乘 120，物理滚一格变成
  120 格。两边对「单位」的理解完全不同，规范文字无法指导实现。
- **影响面**：跨端滚动速度错乱；高精度滚轮/触控板在两端表现不一致；第三方
  按规范实现必然与现有客户端对不上。
- **建议修法**：把单位改成「行/格」（1 = 一格），给出各平台原生单位的换算
  （Windows `delta/120`、macOS line delta 原样）；若要支持像素级平滑滚动，
  另加能力位与独立字段，不要复用现有 `SCROLL` 语义。三端现在统一按「格」：
  Windows 捕获 `delta/120`、注入乘回 120；macOS 捕获 line delta、注入 `.line`；
  Linux 捕获/注入直接用 evdev `REL_WHEEL/REL_HWHEEL`（值就是格），不再乘 120。
  跨端 1:1 已恢复；§5.3 的注释已改为「行/格」并说明各平台换算。像素级平滑
  滚动若要支持，仍需新增能力位与独立字段。
- **状态**：已统一（2026-10-21，规范 + Windows/macOS/Linux 三端实现）。
